This repository is the open-source HITL<sub><i>y</i></sub> server. Self-hosting includes the inbox, projects, plugins, audit log, API keys, and team membership. There are no usage caps.

## Run locally

```bash
yarn install
cp apps/app/.env.example apps/app/.env.local
yarn db:up
yarn db:migrate
yarn dev:app
```

The marketing/docs site is optional (`yarn dev:web`). The Expo reviewer app is `yarn dev:mobile` — see [Mobile](/docs/mobile).

## Telemetry

We don't collect telemetry or usage data anywhere.

Next.js CLI telemetry and Turborepo CLI telemetry are **always off** (`NEXT_TELEMETRY_DISABLED=1` and `TURBO_TELEMETRY_DISABLED=1`), whatever `HITLY_TELEMETRY` says. That is applied on Next config, `yarn` scripts via `scripts/with-hitly-telemetry.sh`, systemd units, and `scripts/systemd/ensure-up.sh`. Docker Compose only runs Postgres, not HITLy. If you add a Dockerfile, set both `*_TELEMETRY_DISABLED=1` in the **build** and **runtime** stages (or run those stages through the wrapper).

`HITLY_TELEMETRY` only turns on the marketing-site Plausible page script. Unset (the default) renders no script tag and makes no analytics request. The value is trimmed; only `1` or `true` turn it on (anything else, including `TRUE`, `yes`, and blank, stays off). The inbox (`apps/app`, http://localhost:3001) never loads Plausible.

Plausible settings are baked in at **build** time. Changing `HITLY_TELEMETRY`, `NEXT_PUBLIC_PLAUSIBLE_DOMAIN`, or `NEXT_PUBLIC_PLAUSIBLE_SRC` requires a rebuild (`yarn build`); restarting the process is not enough.

When `HITLY_TELEMETRY` is on, Plausible still needs both domain and src from env (no hardcoded defaults). hitly.net example only:

```bash
HITLY_TELEMETRY=1
NEXT_PUBLIC_PLAUSIBLE_DOMAIN=hitly.net
NEXT_PUBLIC_PLAUSIBLE_SRC=https://click.hitly.net/js/script.js
```

## Account security

Signed-in users manage email, password, authenticator-app MFA, and passkeys at **Settings → Security**.

**Passkeys** (WebAuthn) sign you in with a device credential instead of a password. Adding or removing a passkey asks for your current password. Registration and sign-in require **user verification** (biometric, PIN, or device passcode), so a passkey is a phishing-resistant multi-factor credential and does not prompt for the authenticator-app code.

The WebAuthn relying-party ID and origin are the hostname and origin of `BETTER_AUTH_URL`. Optional `HITLY_WEBAUTHN_RP_NAME` is a display name only.

## Database

Local Compose runs **Postgres 16** (`postgres://USER:PASSWORD@localhost:5432/hitly`; `apps/app/.env.example` ships the local dev defaults). OSS does not enable row-level security or envelope encryption; those are Cloud overlay concerns.

Older self-host installs used MariaDB. There is no in-place upgrade: stand up Postgres, run `yarn db:migrate` on an empty database, and re-create workspaces. Schema was squashed to a single Postgres migration.

## Rate limiting

Rate limiting is **shared through Postgres**: every app process counts into the `rate_limit_buckets` table (migration `0015`), so limits hold across replicas instead of resetting per process. One atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` per request opens or extends a fixed window; expired rows are swept opportunistically from the same path (at most once every 5 minutes per process), so no cron is required.

Buckets are keyed by `SHA-256(route + NUL + subject)` — raw IPs, emails and API keys are never stored or logged; the `route` column only names the family (`auth`, `mfa-reauth`, `mfa-verify`, `password-change`, `passkey-reauth`, `email-change`, `resend-email-verification`, `reset-check`, `reset-check-shared`, `reset-email`, `ingest`). Every limited answer is a `429` with a `Retry-After` header in seconds.

When the database is unavailable the limiter logs one line per process and transparently falls back to per-process counting — endpoints stay protected, limits just become per-node until Postgres returns. Set `HITLY_RATE_LIMIT_DB=0` to force per-process counting everywhere (e.g. to run without migration `0015`).

Per-family limits and windows come from env (whole numbers; invalid values fail fast at start naming the variable), defaulting to the constants shipped with each route:

| Variable | Default | Covers |
| --- | --- | --- |
| — (no override) | Better Auth's own per-endpoint rules | `/api/auth` endpoints, counted through `customStorage` (hashed client IP + path) |
| `HITLY_RATE_LIMIT_MFA_REAUTH_LIMIT` / `_WINDOW_MS` | 10 / 15 min | MFA re-auth challenges |
| `HITLY_RATE_LIMIT_MFA_VERIFY_LIMIT` / `_WINDOW_MS` | 10 / 15 min | TOTP verify attempts |
| `HITLY_RATE_LIMIT_PASSWORD_CHANGE_LIMIT` / `_WINDOW_MS` | 10 / 15 min | password changes |
| `HITLY_RATE_LIMIT_PASSKEY_REAUTH_LIMIT` / `_WINDOW_MS` | 10 / 15 min | passkey re-auth |
| `HITLY_RATE_LIMIT_EMAIL_CHANGE_LIMIT` / `_WINDOW_MS` | 10 / 15 min | email changes |
| `HITLY_RATE_LIMIT_RESEND_EMAIL_VERIFICATION_LIMIT` / `_WINDOW_MS` | 5 / 15 min | verification resends |
| `HITLY_RATE_LIMIT_RESET_CHECK_LIMIT` / `_WINDOW_MS` | 30 / 60 s | reset-token checks per client (`HITLY_RATE_LIMIT_RESET_CHECK_SHARED_*`, default 600 / 60 s, caps clients with no usable address) |
| `HITLY_RATE_LIMIT_RESET_EMAIL_LIMIT` / `_WINDOW_MS` | 5 / 60 min | reset emails per account |
| `HITLY_RATE_LIMIT_INGEST_LIMIT` / `_WINDOW_MS` | 120 / 60 s | `POST /api/v1/approvals` per API key |

`HITLY_RATE_LIMIT_AUTH_ENABLED=1|0` forces Better Auth's own limiter on or off; the default keeps its production-only behaviour. The MCP server limits per API key in-process by default; set `HITLY_MCP_DATABASE_URL` to count through the same shared table (tune with `HITLY_MCP_RATE_LIMIT` / `HITLY_MCP_RATE_LIMIT_WINDOW_MS`).

## What is not in this repo

Stripe billing, hosted plan limits, and SSO ship in a private `@hitly/cloud` overlay used by [hitly.net](https://hitly.net). The `@hitly/cloud` package here is a stub: billing API routes return 404, and the nav hides Cloud-only items.

Do not set an env var to "enable Cloud." Cloud features exist only when that private package replaces the stub.

## Housekeeping

The app process runs due jobs about once a minute:

| Job | Schedule | What it does |
| --- | --- | --- |
| `expire-overdue-approvals` | hourly | Marks pending items past `expiresAt` as `expired` |
| `purge-completed-approvals` | daily | Deletes closed items older than the workspace plan retention |
| `purge-expired-audit-events` | weekly | Deletes project events older than `auditRetentionDays` |

Self-hosted workspaces keep completed items forever. Cloud (invite-only) plans: solo 10 days, pro 30, team 365, enterprise 1000.

Set `HITLY_HOUSEKEEPING=0` to disable the in-process timer (for example when a process manager or cron should own it). Then `POST /api/v1/housekeeping` with `Authorization: Bearer $HITLY_CRON_SECRET`. Optional JSON `{ "job": "purge-completed-approvals", "force": true }` runs one job immediately.

## Outbound destinations

HITLy sends requests to destinations you configure: HTTP and S3 evidence sinks, workspace OTEL endpoints, and plugin URLs (for example a Mastra or LangGraph base URL, or an HTTP resume URL). Every request runs a destination check when it is sent:

- Only `http` and `https` URLs are accepted, without a user name or password in the URL.
- The host name is resolved once, every address is checked, and the request goes to that checked address.
- Redirects are not followed; a 3xx answer is reported as an error.
- The connection must open within 5 seconds and the whole request must finish within 10 seconds (5 seconds for evidence sinks and OTEL, 60 seconds for plugin resume calls). Responses are capped at 1 MiB.
- Error messages name the status code and host only, never the response body or the full URL.

Private, loopback and link-local addresses (including `localhost`) are allowed when `NODE_ENV` is not `production`, so local development and the quickstart work as they are. In production they are refused unless the server sets:

```bash
HITLY_ALLOW_PRIVATE_EVIDENCE_SINKS=true
```

Only the exact value `true` turns this on. It is read from the server environment, not from workspace or project settings, and the server logs one line at startup when it is on. Set it on a self-hosted production server whose evidence sink, collector or agents run on the same machine or private network. Multicast and broadcast addresses are always refused.
