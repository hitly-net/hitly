# HITLy weekly changelog — 7 November 2026

**Reporting window:** 31 October 2026 through 7 November 2026 (UTC).

This week's merged work lands reviewer-visibility rules from the HITL spec into HITLy's approval evidence chain, and tightens the spec itself around single-use responses. All items below are **merged to `main`**; no public release was published in this window, and HITLy Cloud remains in closed beta.

## Approval evidence: who saw it, who decided, from where

The `hitly.evidence.v1` chain records two things it previously did not:

- **When an ask was first shown.** A `presented` event is now recorded once per approval when a user who can decide first opens the approval detail page (web) or screen (mobile). The chain order `requested -> presented -> decided -> resumed` always holds: a decision that arrives with no prior `presented` gets one recorded immediately before it, in the same transaction.
- **Who decided, on which device.** `decided` events now carry a `decidedBy` actor block alongside the existing reviewer id, plus optional client information (`channel` of web/mobile/api, platform, app version, user agent). The same client block can appear on `presented`.

As described in the PR: no IP addresses are recorded, `presented` means *opened* rather than *read*, and browsing readers cannot mark approvals. The new fields are optional, so content hashes of pre-existing events are unchanged, and a retry reuses the stored decider and device rather than relabelling the original. The accompanying database migration is additive and nullable, with no backfill.

The PR reports lint, typecheck, 818 tests and build passing at merge time. This is code merged to `main`, not a deployed feature.

Sources: [hitly#97](https://github.com/hitly-net/hitly/pull/97), merge commit [94b2e92](https://github.com/hitly-net/hitly/commit/94b2e9246aa0798854b3b95208dc07684770ac03).

## Spec: a response can only be spent once

A docs-only change to `SPEC.md` (7 added lines, no schema, example or test-vector changes) closes a gap where a conformant requester could honour one approval twice after a restart:

- **§3.8 Action binding:** a response that authorises an action is single-use. The requester must durably record the use of the `requestId` before acting and must not act again on it, including after a restart. If the process dies after the record but before or during the action, the outcome is *unknown*: verify the effect or raise a new request; never quietly count it as done or failed.
- **§3.2 Identifiers:** hosts should expose how long they retain create-once records (`idempotencyKey` or equivalent); requester single-use records should last at least as long as that window.
- **§4.2 Status:** a request is terminal once it has a response — re-submitting always creates a new `requestId`, never mutates the old one.
- **§15 Open questions:** post-decision disposition and long-lived grants are recorded as parked items.

Source: [hitl-spec#10](https://github.com/hitly-net/hitl-spec/pull/10), merge commit [a4c7d22](https://github.com/hitly-net/hitl-spec/commit/a4c7d22c69eaab3940f3be7d4bff11c190aa8693).

## Spec: a conformance check that survives a real kill

Building directly on the single-use rule above, a community contribution adds `examples/conformance/replay-after-restart/` to the spec repo: a standalone runner (`node run.mjs <command>`) that checks whether a requester remembers a spent response across a genuine process death. Five cases cover replay in-process, replay after restart, kills before and after the action, and a deliberately broken memory-only control that proves the check can fail. The kill is a real SIGKILL from a separate process, effects are counted outside the killed process, and any requester in any language can be tested against it.

The author notes the checks were run on Windows with Node 24 and are not yet wired into the repo's validate script or CI.

Source: [hitl-spec#11](https://github.com/hitly-net/hitl-spec/pull/11), merge commit [3410edaf](https://github.com/hitly-net/hitl-spec/commit/3410edaf4458138e4afff91cab1cf4edd39ed578).
